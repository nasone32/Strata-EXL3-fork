# AMD community-test snapshot: validation

Measured on 2026-10-26: Linux, ROCm core-7.14, Ryzen 9 7950X (16 physical cores, 32 logical CPUs), two RX 7900 XTX cards (gfx1100), Qwen3.8-NEXT EXL3 3 bpw. The peer retained its 4096 MiB reserve. This is not RDNA4 or NVIDIA validation.

## Defaults and correctness

The neutral EXL3 optimization switches were removed from the benchmark environment; the recommended RDNA switches remained explicitly enabled. With the new engine defaults, warm CODE/PROSE decode measured 75.69/62.13 tokens/s. The preceding explicit optimized preset averaged 75.66/62.97 tokens/s across two sessions. Generated token IDs matched exactly for both prompts and both turns. CODE requested `write a bubblesort algorithm in C code`; PROSE requested `explain a PID controller ELI5`; seed 1234, temperature zero, natural stop, 2048-token limit. Turn zero warmed the cache, turn one supplied the reported decode rate.

The clean source folder configured and built the HIP engine successfully. Build artifacts were kept outside this source folder. Validation used an existing local llama.cpp source tree through `STRATA_GGML_DIR`; a fresh network fetch of the pinned dependency was not tested.

Six EXL3 tests passed in the development build: `exl3_flags_test`, `exl3_loader_validation`, `exl3_moe_multi_parity`, `exl3_peer_test`, `peer_adapt_plan_test`, and `exl3_route_plan_test`. The final clean-folder alias-resolution test passed, including explicit-zero handling and scoped-versus-legacy precedence. Tests used `HIP_VISIBLE_DEVICES=0,1` to exclude the integrated GPU.

The final clean-folder binary passed the 512-token synthetic needle fixture with a 48-token answer limit. The real configuration generated by `run-peer.sh --dry-run`, with model/tokenizer/MTP paths supplied at runtime, also passed that fixture. No user-specific model paths were written into this source folder.

CPU-only setup regressions: `tools/test_setup_amd.py` passed 36 tests and `tools/test_setup_choices.py` passed 47. An EXL3 setup wizard and its corresponding setup-specific tests do not yet exist; use the fork launchers, not the upstream GGUF setup flow, for EXL3.

## CPU affinity

Each setting used two full CODE/PROSE sessions, with the initial three settings run in forward and reverse order. The same pre-change binary was used throughout. All output IDs matched.

| Auxiliary thread placement | CODE tokens/s | PROSE tokens/s |
|---|---:|---:|
| Explicit `20-23` | 75.66 | 62.97 |
| Explicit `off` | 75.43 | 62.48 |
| Explicit `28-31` | 75.16 | 62.54 |
| Old unset behavior (`auto`) | 72.19 | 60.94 |

The `20-23` advantage over true `off` is only 0.3%/0.8%, too small to establish a robust win with this sample. Leaving affinity off is the portable default. `20-23` remains a tested candidate for this CPU topology: these logical CPUs are SMT siblings of physical cores 4–7. Sixteen physical cores alone do not imply the same numbering or optimum. Tune on each machine.

## Limits

- RDNA4 EXL3 optimized kernels have not been validated or extended by this change. Existing compile/runtime capability gates still apply; setting an environment switch is not proof that its kernel ran.
- CUDA and SYCL were not built: their compilers are unavailable here. Windows EXL3 support remains limited by the POSIX safetensors accessor.
- This validation covers the 3 bpw model. Earlier 4 bpw measurements belong to the preceding speed-stack work; the final defaults snapshot has not received a full 4 bpw regression run.
- A cold file cache can still make expert staging slow. The engine does not eagerly load the entire model into RAM. Dense weights reside in VRAM, experts use reclaimable host file cache, and the recommended PLE mode is direct SSD IO.
- The earlier dense-page release log overcounts bytes because duplicate tensor ranges are counted repeatedly. Do not interpret its number as measured RAM savings; range accounting needs a follow-up correction. The repeated advice is idempotent and does not change tensor values.
